# Trade Execution Technical Design

## Scope and assumptions

The implementation completes `POST /api/trades/execute` using the existing Spring Boot service structure, MyBatis mappers,
and H2 database. It executes immediate BUY and SELL trades for the configured active cryptocurrency pairs based on the best
bid/ask price.

# Assumptions
1. No order matching algorithm is implemented, all orders are assumed to be pure market orders executed against
the current market price.
2. Assume that authentication is handled by an external service – as stated in the business requirements, requests are assumed to be pre-authenticated.
3. Assume that the userId in the request is the userId of the requesting user.
4. Assume that the user has zero balance for the symbol if wallet balance database entry does not exist.

## API contract

The request contains:

| Field | Meaning |
| --- | --- |
| `userId` | Existing user ID |
| `tradeType` | `BUY` or `SELL` |
| `quantity` | Amount of the base cryptocurrency to trade |
| `cryptoPair` | Pair name, such as `ETHUSDT` |

The controller returns HTTP 200 with `userId`, `tradeId`, `tradeType`, `cryptoPair`, `quantity`, `price`, and `totalAmount` after successful execution.
The trade ID is generated by H2 and populated through MyBatis generated-key support.

## Execution flow

Request-field validation runs at the HTTP boundary through the controller's `@Valid` and the DTO constraints, backed by `spring-boot-starter-validation`. Direct service callers must supply a valid request. The service retains business checks for user existence, pair availability, prices, and sufficient balances.

`TradeServiceImpl.executeTrade()` performs the following steps inside a Spring-managed transaction:

1. Select and lock the user row using `SELECT ... FOR UPDATE`. Reject the request if the user does not exist.
2. Look up the requested pair and reject missing or inactive pairs.
3. Retrieve the latest stored prices and select the entry matching the requested pair ID. Reject execution when no matching price exists.
4. Read the user's wallets and resolve the base and quote balances by symbol ID. A missing wallet is treated as having zero balance.
5. Check that the spending wallet has sufficient balance to cover the trade.
6. Insert the trade record with the selected price and calculated total amount into the database. 
7. Upsert the quote wallet, followed by the base wallet.
8. Log the trade ID and construct the response. Spring commits the transaction before the controller receives the successful return value.

## Pricing and balance calculations

The base asset is BTC or ETH, and the quote asset is USDT. 
Quantity is expressed in units of the base asset. Prices come from the existing price aggregation system.

| Operation | Execution price | Required balance | Base balance after trade | Quote balance after trade |
| --- | --- | --- | --- | --- |
| BUY | Ask price | Quote balance >= quantity × ask price | Base + quantity | Quote − total amount |
| SELL | Bid price | Base balance >= quantity | Base − quantity | Quote + total amount |

Equality is allowed: a user may spend the entire available quote balance or sell the entire base balance.

Calculations use `BigDecimal` as per the existing convention. 
Balance validation, trade recording, and wallet updates use the same selected price object. 
The total is calculated as quantity multiplied by the applicable price.

## Wallet creation

`UserWalletMapper.upsertBalance()` uses H2 `MERGE INTO ... KEY (user_id, symbol_id)`. It updates an existing wallet or inserts a missing wallet. 
The unique user-symbol constraint prevents duplicate wallet records, and the operation updates `updated_at`.

For a valid positive trade, a missing spending wallet has zero balance and is rejected. 
A missing receiving wallet starts at zero and is created when the user acquires that asset. 
For example, a first ETH purchase creates the ETH wallet while debiting the existing USDT wallet.

## Transactions and consistency

`executeTrade()` is annotated with `@Transactional(rollbackFor = Exception.class)`. 
Through the Spring service proxy, the user lock, balance reads, trade insert, and both wallet upserts participate in one transaction.

If trade insertion or either wallet update throws an exception, the transaction rolls back. 
A failure during the second wallet update must therefore leave no new trade record and must undo the first wallet update. 
Spring also rolls back on Java `Error` instances by default.
This ensures data consistency and atomicity.

The service's success log occurs after the transaction commit is performed successfully, and can be used as an indicator of
a successful trade.

## Concurrent trading

The service locks the existing user row before reading wallet balances. 
Trades for the same user wait until the preceding transaction commits or rolls back, then read the committed balances. 
This also coordinates BTCUSDT and ETHUSDT trades sharing the same USDT wallet. Different users can proceed independently.

The user row is locked instead of individual wallet rows because receiving wallets may not yet exist. 
A single user lock protects the entire read-check-write operation, including creation of missing wallets, without acquiring multiple wallet locks.

Every future operation that changes a user's wallets must acquire the same user lock within its transaction. 
Locking a user does not automatically lock all of that user's wallet rows; protection depends on this shared convention. 
Database lock timeouts currently propagate as failures; there is no application retry policy.

## Audit history

The trade table records the user, pair, BUY/SELL type, quantity, execution price, total amount, and a database-generated `trade_time`. 
The mapper inserts trade records and exposes no update or delete operation as there is no such needs currently. 
This execution flow leaves committed trade history unchanged, although database-level immutability is not separately enforced.

The timestamp represents database insertion time within the transaction, and this is included in the trade response as well.

## Current error behavior

The service throws Tomcat's `BadRequestException` for unknown users, missing or inactive pairs, and insufficient balances. 
Missing prices throw Java `InternalError`. Database exceptions propagate.

## Verification

Mockito unit tests cover successful BUY and SELL calculations, trade contents, wallet upsert arguments, insufficient balances, 
unavailable pairs and prices, database failures, decimal arithmetic, and acquiring the user lock before wallet reads and writes.

`TradeApplicationTests` uses the real Spring context, MyBatis mappers, and a dedicated in-memory H2 database. Its trading integration tests cover:

- ETH BUY through MockMvc, including creation of the receiving wallet and persisted audit fields.
- BTC SELL through MockMvc, including both balance updates and the persisted trade.
- Insufficient balance leaving the database unchanged.
- A database constraint failure during the second wallet update rolling back the trade and first wallet update.
- Two concurrent BUY attempts whose combined cost exceeds available USDT: exactly one succeeds, one is rejected, and final balances and history reflect one trade.

The integration suite also covers missing required fields, zero and negative quantities, and blank pairs returning HTTP 400 without database changes. 
The concurrency test checks two competing trades; it does not establish the documented throughput or latency targets.

Run the trading tests with Java 21:

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 21)
./mvnw -Dtest=TradeServiceImplTest,TradeApplicationTests test
```

## Remaining limitations
- Add explicit HTTP exception handling for service failures. Invalid DTO requests already return HTTP 400 through Spring MVC validation.
- Define quantity precision and a consistent rounding policy. H2 stores monetary amounts as `DECIMAL(20,8)`, but the service does not constrain scale or round totals before persistence. Stored amounts can differ from unrounded response values.
- Define an acceptable price age. The service uses the latest stored price without checking freshness, so stale historical prices may be used after exchange fetch failures.
- Resolve ties in latest-price timestamps deterministically. The current query can return multiple records for a pair sharing the newest timestamp; the service takes the first matching record.
- H2 is currently configured as an in-memory database. History persists within the running application but is not durable across restarts with the supplied configuration.
- Performance and availability targets have not been verified by load testing.
